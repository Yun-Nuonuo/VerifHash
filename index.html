About VerifHash

A blockchain project developed with transparency and verifiable progress.

VerifHash (VSH) is an independent blockchain project based on the VerusCoin codebase. It aims to establish its own network identity, consensus parameters, and economic model.

Its planned consensus model combines Proof-of-Work (PoW) and Proof-of-Stake (PoS), allowing both mechanisms to compete in block production under the network's consensus rules.

The project is independently developed and is not affiliated with, endorsed by, or officially supported by the VerusCoin team.

Development is ongoing. Design decisions, implementation, and test results are treated as separate milestones.

Development Roadmap

Built on the VerusCoin codebase. Foundation first, testing and launch later.

  1. 01

    Source Code Audit & Fork Boundaries

    Understanding the project structure before making major changes.

    Tasks
    • 1.1Map the architecture and major source code components
    • 1.2Identify components to retain, modify, or replace
    • 1.3Review and document changes already made
    • 1.4Establish a documented source build baseline
    • 1.5Create a baseline and recovery procedure for failed changes
    • 1.6Run the upstream test suite as a pre-consensus-change baseline
    • 1.7Complete the license compliance and source attribution audit
    • 1.8Define a policy for integrating upstream security fixes

    Completion criteria: source structure, documented changes, build and test baseline, licensing obligations, and upstream maintenance policy are reviewed.

  2. 02

    Chain Identity & Network Separation

    Giving the new coin its own identity and preventing unintended interaction with the original network.

    Tasks
    • 2.1Define the coin name, ticker, and chain identity
    • 2.2Review address prefixes and encoding formats
    • 2.3Define network magic bytes, P2P ports, and RPC ports
    • 2.4Review coin type and relevant wallet parameters
    • 2.5Separate data directories, configuration, and wallet storage
    • 2.6Audit remaining embedded Verus identity references
    • 2.7Verify that mainnet, testnet, and regtest are fully isolated

    Completion criteria: chain identity is consistent and all network modes are proven to use the correct independent parameters and data.

  3. 03

    Consensus Design & Tokenomics

    Defining the rules that determine block validity and coin issuance.

    Tasks
    • 3.1Select a hybrid Proof-of-Work (PoW) and Proof-of-Stake (PoS) consensus design in which both mechanisms compete for block production
    • 3.2Set the target block time (design target: 150 seconds)
    • 3.3Define difficulty adjustment requirements for changing network hashrate
    • 3.4Set the initial block reward (design target: 25 VSH)
    • 3.5Set the halving interval (design target: 840,960 blocks)
    • 3.6Calculate the planned emission schedule and estimated maximum supply
    • 3.7Define reward rounding and the smallest coin unit
    • 3.8Specify coinbase, reward, and supply validation requirements
    • 3.9Audit all code paths that determine rewards and supply
    • 3.10Choose the launch model: fair launch, premine, or development fund
    • 3.11Verify the PoW/PoS block selection and reward rules in the implementation
    • 3.12Decide which inherited features to retain or remove

    Completion criteria: consensus and emission rules are documented, internally consistent, implemented, and validated through tests. The estimated supply remains a design calculation until confirmed by the implementation.

  4. 04

    Genesis Block & Network Parameters

    Establishing the blockchain starting point and its network-specific parameters.

    Tasks
    • 4.1Define the genesis block parameters
    • 4.2Implement separate genesis block configurations for VSH networks
    • 4.3Verify genesis hashes and Merkle roots independently
    • 4.4Verify network parameters and chain identity across all modes
    • 4.5Verify ports, magic bytes, and data directories
    • 4.6Confirm nodes cannot accidentally use the original network genesis or configuration

    Completion criteria: genesis data and network parameters are independently verified and consistent with the intended chain configuration.

  5. 05

    Regtest & Consensus Testing

    Proving that the core rules work locally before running a public testnet.

    Tasks
    • 5.1Run nodes with separate data directories
    • 5.2Generate local blocks and verify block height
    • 5.3Test transaction and block validation
    • 5.4Test rewards at different block heights
    • 5.5Test reward changes at halving boundaries
    • 5.6Test rejection of invalid blocks and transactions
    • 5.7Test node restarts and blockchain reloads
    • 5.8Verify regtest cannot modify data belonging to other networks
    • 5.9Simulate chain reorganizations and double-spend attempts
    • 5.10Fuzz block and transaction validation

    Completion criteria: automated and manual tests demonstrate that consensus rules behave as designed, including under adversarial scenarios.

  6. 06

    Multi-Node Testnet

    Proving that multiple nodes can operate as one network.

    Tasks
    • 6.1Run at least two nodes in separate environments
    • 6.2Test peer connections and block propagation
    • 6.3Test transaction propagation
    • 6.4Verify that nodes agree on the valid chain
    • 6.5Test connection recovery and resynchronization
    • 6.6Check configuration conflicts and network separation
    • 6.7Document test results and discovered bugs
    • 6.8Test fork and reorganization scenarios across nodes

    Completion criteria: multiple nodes connect, synchronize the chain, and validate blocks using the same consensus rules.

  7. 07

    Security Audit & Release Readiness

    Assessing whether the implementation is ready for a potential public release.

    Tasks
    • 7.1Audit transaction and block validation
    • 7.2Audit rewards, emission, and maximum supply
    • 7.3Review RPC security and node configuration
    • 7.4Review wallet security, backups, and data recovery
    • 7.5Prepare node build and installation documentation
    • 7.6Prepare release and network monitoring procedures
    • 7.7Resolve critical bugs before considering launch
    • 7.8Request an independent third-party security audit
    • 7.9Establish a security vulnerability reporting or bug bounty program
    • 7.10Publish signed releases, checksums, and reproducible build instructions
    • 7.11Seek legal guidance regarding public cryptocurrency regulations

    Completion criteria: no known critical issues remain, independent audit results are available, testing is documented, and operational procedures exist.

  8. 08

    Ecosystem & Community

    Preparing the supporting infrastructure for a usable and growing network.

    Tasks
    • 8.1Set up seed nodes and DNS seeds
    • 8.2Build a block explorer
    • 8.3Provide a wallet and user documentation
    • 8.4Prepare mining software and mining pool support
    • 8.5Publish public documentation and a technical whitepaper
    • 8.6Open community channels and security reporting procedures

    Completion criteria: users can run nodes, participate in mining or staking, and send transactions without direct assistance from the core team.
